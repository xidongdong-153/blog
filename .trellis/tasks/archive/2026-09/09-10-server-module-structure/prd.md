# 服务端目录与职责整理

## 目标

让维护者能按业务找到服务端代码，明确 HTTP 处理、业务动作和数据访问分别放在哪里。本轮交付设计与实施计划，不修改产品代码；进入实施需要用户再次明确批准。

## 背景事实

- 项目是单包 Next.js 应用，服务端使用 Hono、Better Auth、Drizzle 和 libSQL，实际依赖与命令见 `package.json`。
- `src/server/routes/index.ts:10` 注册 system、presence、links、config、comments、auth、ai 七组路由。
- `src/server/routes/links.ts:64`、`:164`、`:205` 同时处理 HTTP、申请、审核、数据库与通知；友链页、审核页和状态页另有直接数据访问。
- comments 和 AI 已有 service，但客户端类型从 service 导入；`config/auth` 只提供认证相关信息。
- 部分旧规范仍写着未挂载 Hono、没有 service 或数据库，与源码冲突。证据和调用点统一记录在 [调研文件](research/current-structure.md)。

## 要求

- **R1：路由按目录组织。** 不同业务路由有明确目录归属，不再把所有域路由平铺在一起。
- **R2：route 与 service 职责明确。** route 处理 HTTP，业务规则和数据访问由 service 负责。维护者不需要在页面和路由各改一份相同规则。
- **R3：评估业务模块组织。** 给出适合当前项目规模的单一推荐结构，说明为何不只做全局分层或增加完整多层模板。
- **R4：不做兼容。** 一次替换旧结构并更新所有调用点。删除旧文件、旧导出和旧实现，不留 re-export 转发、路径别名、适配层、双套实现或版本过渡。
- **R5：包含散落的服务端逻辑。** 用户确认纳入友链页、审核页、状态页的数据逻辑和邮件实现；页面布局不动。

## 范围

后续实施涉及 `src/server/`、`src/lib/email.ts`、相关页面的数据读取、客户端类型引用、摘要同步脚本导入、测试文件与 `package.json` 测试清单。与新结构直接相关的现有规范在代码验证后更新。

本轮只写当前任务目录的需求、设计、计划、调研和上下文清单。用户已允许当前会话直接完成调研和设计；该授权不包含源码实施或提交。

## 不做

- 不新增业务功能，不重新设计 URL、响应协议、权限产品规则或页面布局。
- 不拆独立后端或 monorepo，不升级依赖，不增加测试框架。
- 不引入 DI 容器、通用 repository、controller 或为了凑层数而建立的空文件。
- 不修改数据库 schema、迁移历史或部署方式，不执行真实邮件、模型调用或生产数据操作。
- 不重写邮件模板、不顺手处理并发策略、全站文案或其他无关问题。

## 验收条件

| 条件 | 对应要求 | 可检查的结果                                                                                           |
| ---- | -------- | ------------------------------------------------------------------------------------------------------ |
| AC1  | R1       | 设计覆盖现有七组路由；实施后每组路由都有业务目录和唯一挂载位置                                         |
| AC2  | R2       | 业务 route 不直接访问 DB、邮件或模型驱动；service 不依赖 Hono Context 或 Next 页面 API                 |
| AC3  | R3       | 设计给出业务模块的推荐划分、依赖方向和不增加多余层的理由                                               |
| AC4  | R2、R5   | 原业务断言继续有效，新增被拆分入口的测试；实施后类型、Lint、格式、隔离测试和构建通过，未通过项如实报告 |
| AC5  | R1—R5    | `prd.md`、`design.md`、`implement.md`、调研和上下文清单齐全并经评审；未获实施批准时状态保持 `planning` |
| AC6  | R4       | 旧目录、旧源码路径和旧导出不存在；产品代码、脚本和测试没有旧引用，没有兼容实现                         |
| AC7  | R5       | 友链页、审核页和状态页调用所属 service；邮件实现位于 server infra；页面差异只涉及取数、类型和字段引用  |

规划完成不等于上述代码验收已经通过。实施时按 [implement.md](implement.md) 记录实际结果，技术边界以 [design.md](design.md) 为准。
